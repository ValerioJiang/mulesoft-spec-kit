# Salesforce domain adapter

This is the workspace-owned adapter for Salesforce. The design stages (`/speckit-salesforce-specify`, `-clarify`, `-plan`, `-review`) use this adapter and the `salesforce` commands only; they do not depend on any other extension. When the optional `sf-workspace` extension is installed, its extended stages (`/speckit-sf-workspace-*`) read this adapter first and then `.specify/extensions/sf-workspace/WORKSPACE-CONTRACT.md`; they extend the artifacts produced here and never replace them. Do not invoke upstream SFSpeckit commands against a Salesforce repository's `.specify/` directory.

Before acting on any stage, read `spec-kit-workspace.json`, this adapter, `.specify/extensions/technical-solution/docs/workflow-contract.md`, and the selected initiative's common artifacts. Apply the central workspace contract wherever paths, project layout, configuration, aliases, tools or approvals are concerned.

Keep every lifecycle artifact under the initiative root declared by `artifact_layout` in `spec-kit-workspace.json` (by default `initiatives/<id>/salesforce/`); shared intent and cross-domain decisions go to `initiatives/<id>/common/`. Resolve the selected repository with the shared CLI declared by `spec-kit-workspace.json`, using an exact source workspace ID or explicit root. It may be any Salesforce repository. Inspect the verified Git root returned by the resolver and `sfdx-project.json`, then map package paths from `packageDirectories`. Never assume a fixed application directory, `force-app/`, fixed package names, org aliases, tracker projects, branch conventions or a Git host.

Lifecycle artifacts include `spec.md`, `clarification-report.md`, `plan.md`, `data-model.md`, `tasks.md`, story files when the project's workflow needs them, `implementation-log.md`, `verification/`, `review.md`, and `release.md`.

Use only the connected Salesforce read-only capability explicitly available in the current session for org facts it supports. Do not retrieve business records. For code stages, use the project's own source paths, toolchain and conventions for local implementation and tests. Record the exact commands and evidence. Keep proposed tests distinct from executed test results. Apply an optional organisation profile from `.specify/profiles/` only when the initiative explicitly selects it; otherwise use the agnostic Salesforce adapter and never inherit organisation rules silently.

An explicitly invoked implement/verify/review/deploy/UAT command operates only on the selected initiative and application repository. It must report the exact files, commands, environment and evidence. Direct user authorization is required for deployment and any external write such as issue creation, PR/MR, org changes or other Salesforce mutations. Never deploy to an inferred target. Follow the selected project's own release policy; never assume development/QA/production aliases.
