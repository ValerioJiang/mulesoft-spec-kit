# MuleSoft domain adapter

This workspace-owned adapter covers the same lifecycle as Salesforce while using MuleSoft-specific artifacts. Read `spec-kit-workspace.json`, this adapter, the central workflow contract at `.specify/extensions/technical-solution/docs/workflow-contract.md`, the lifecycle overview at `.specify/extensions/technical-solution/docs/lifecycle.md` and the selected initiative's common artifacts before acting. All MuleSoft design, task, verification and release artifacts stay under the initiative root declared by `artifact_layout` in `spec-kit-workspace.json` (by default `initiatives/<id>/mulesoft/`); cross-domain requirements remain under `initiatives/<id>/common/`. Implementation targets are resolved from the initiative's configured MuleSoft repository or repositories.

Resolve an application only through the shared CLI declared by `spec-kit-workspace.json`, using an exact workspace ID, `<workspace-id>:<relative-repository-path>`, or its explicit-root option for one-off roots. The CLI owns local config parsing, registered manifest adapters, path containment and nested Git-root verification. Commands must not parse the local registry or the catalog manifest, treat a workspace catalog as an application repository, select the first entry, search the filesystem, or clone when a mapping is absent. Discover the selected application's actual layout, layer, `pom.xml`, `mule-artifact.json`, API contracts, dependencies, toolchain, deployment model and tests only after the resolver returns the Git root. Do not assume a repository name, application inventory, API-led layer or shape, Mule/Java/plugin or runtime version, directory layout, Anypoint organization, environment or deployment target. Keep Experience, Process and System responsibilities separate only where ownership and evidence support them.

Lifecycle artifacts include `spec.md`, `clarification-report.md`, `plan.md`, `contracts/`, `tasks.md`, `analyze.md`, `implementation-log.md`, `verification/`, `review.md`, and `release.md`. Contract drafts are labeled `DRAFT — NOT PUBLISHED` until their owner and publication approval are recorded.

For implementation, change only tasks approved in the central `tasks.md` and files in the selected application scope. Do not execute Maven, MUnit or verification checks in the implement stage; use the explicit QA/verify stage and report the exact command, app, revision and result. MUnit and build commands run only when the user invokes verification or implementation requiring them.

Use repository evidence for source state and connected Anypoint/Exchange/Runtime Manager capabilities only when available. Do not treat a local contract or API file as proof of its published version or runtime state. Mark unavailable live evidence `NOT_EXECUTED`.

Direct user authorization is required for PR/MR, ticket, Exchange publication, Anypoint mutation, deployment and other external writes. Require an explicit target and apply the selected repository's release policy. Never publish a draft contract or infer production readiness.
